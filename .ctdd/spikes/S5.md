## Verdict: **GO for `rmcp` 3.8.0, with the `local` feature**

`rmcp` meets every criterion except the second client, which is not yet tested (see Q2). Tools are declared at runtime with no macro: you implement `list_tools` and `call_tool` on `ServerHandler` by hand and build each `Tool` from a name, a description and a JSON schema object. The **`local`** feature drops the `Send + Sync` bound on the handler and the `Send` bound on its futures. With it, the server holds a non-`Send` store directly and runs on a `current_thread` runtime with a `LocalSet`. Neither the port nor `arbitre-core` changes. The hand-written JSON-RPC fallback (R-9) is not needed.

Reservations:

1. **Requests run concurrently.** Each request is dispatched as its own task (`spawn_local` under `local`). When requests are pipelined, responses come back out of order, and a `notes.list` sent right after a `notes.add` saw the state from before the add. The MCP spec allows this. Each `Store::apply` stays atomic, but ST-07 should decide whether to serialise tool calls (Q1).
2. **Claude Code rewrites dots in tool names**: `notes.add` becomes `mcp__s5__notes_add`. The call still works, but ST-03 should choose catalogue names that survive this mapping (Q3).
3. **The major version churns**: 1.0 (2026-03), 2.0 (2026-06), 3.0 (2026-07). Pin exactly (`=3.8.0`) and plan for a migration about every two quarters.

In `rmcp`, `local` replaces `tokio::spawn` with `tokio::task::spawn_local` (`service.rs`, `spawn_service_task`) and sets `MaybeSend`/`MaybeSendFuture` to empty bounds. Under `local`, the HTTP server transport (`transport-streamable-http-server`) is excluded. That costs nothing here, because v1 only needs stdio.

## Alternatives

None was needed: `rmcp` passes every criterion it was tested on. Credible fallbacks are `rust-mcp-sdk` 2.0.0, a community SDK that was not evaluated, and the hand-written JSON-RPC stdio server from R-9. The fallback costs little, because every catalogue-specific part (schemas, dispatch, errors) is already ours. `rmcp` contributes framing, the `initialize` handshake, version negotiation and the model types.

## Risks

- **Concurrent requests** against a store that is atomic per batch but has no isolation across calls (reservation 1).
- **Major-version churn** (reservation 3). The handler surface we use is small (`get_info`, `list_tools`, `get_tool`, `call_tool`), which limits the cost of a migration.
- **No JSON Schema validation over stdio.** `rmcp` only checks schemas through `get_tool` in its HTTP transport. Arguments must be validated by the catalogue, which we want anyway for parity with the CLI.
- **`local` excludes the HTTP server transport.** If a remote MCP server is ever needed, the handler must become `Send` (a `trait-variant` adapter on the native side, as S1-A anticipated) or run on a dedicated thread.

## Questions for Quentin

**Q1. Should tool calls be serialised in ST-07?**
- (a) Serialise in the handler, with one call at a time behind a local `Mutex`/semaphore. Order is deterministic and INV-28 is easy to reason about.
- (b) Leave calls concurrent, as the spec allows, and rely on per-batch atomicity.
- *Recommendation: (a).* It is a few lines of code, it costs nothing at the volume of an assistant, and it rules out surprising reads.

**Q2. Which second client for the "two clients" criterion?**
- (a) MCP Inspector CLI (`npx @modelcontextprotocol/inspector@2.13.0 --cli`). This spike could not run it, because the permission classifier blocks external code. You can run it, or allow it.
- (b) Another assistant (Codex CLI, Gemini CLI, Cursor).
- (c) A test client built on `rmcp` (feature `client`). This is weak as compatibility evidence because it uses the same SDK.
- *Recommendation: (a) for ST-07's contract test, plus (b) once by hand at acceptance.*

**Q3. How should catalogue names map to MCP tool names?**
- (a) Keep `module.action` and accept that Claude Code shows `module_action`.
- (b) Use `module_action` directly in MCP, mapped from the CLI's `module action`.
- *Recommendation: (b).* It is stable across clients, and parity is still derived from the catalogue.
